# Waypoint: approach and tradeoffs

## What the prototype proves

The product should answer two different questions from the same shipment evidence: **"Will my delivery arrive when promised?"** for a customer, and **"What needs my attention now?"** for operations. The demo uses seven fictional shipments across Bilbao Works and Valencia Hub, two fictional customer accounts, Roadline and OceanSpan, domestic road and international road-sea-road journeys. It includes a customs hold, an overdue delivery, a stale feed, an unknown operator status, an on-track shipment and a completed delivery. A role/account switcher makes the two journeys easy to evaluate; its scope filtering is only a frontend demonstration, never a security boundary.

Depth takes precedence over breadth: a portfolio ordered by exception leads into an evidence-bearing shipment view, a suggested next action and a reviewable customer notice. The customer sees the delivery timeline without internal action acknowledgments, an intelligible advisory and synthetic document previews. Four routed accounts demonstrate distinct site or customer scopes. Operations can add deliveries, confirm their phases sequentially and acknowledge actions with operator-update and actual receipt times. Acknowledgment records an operator action but does not clear the alert or change the delivery status; alerts are derived from shipment evidence and the demo clock, with no manual delete or dismiss action. Pinia holds this state and persists it in browser-local storage across reloads; copy-to-clipboard is the only notice action. There is no send, upload, download, login, live refresh, database or integration.

## What "AI" does here

All intelligence in this prototype is **deterministic simulation**, not a claim of machine learning. Two external operator adapters map different source vocabularies onto shared milestones; an internal Waypoint adapter maps action acknowledgments. The normalized timeline retains the raw code, operator, event time and receipt time. Duplicate source event IDs are removed; the journey orders by event time. Unknown codes remain "needs review" and cannot become a confirmed status. Events after the current scenario clock are not displayed. New operators can supply another adapter without changing the view.

The exception policy flags confirmed customs holds, missed promised dates, updates older than 36 hours, unmapped codes and fixture-defined arrival risk. It ranks them by severity and supplies a reason and a proposed action. Portfolio counts, a short priority summary and suggested action are computed from visible shipments. Simulated natural-language search extracts supported country, reference, delay and next-seven-days constraints; it does not claim to understand arbitrary questions or query hidden accounts. The fixture's revised ETA is labeled **scenario estimate, not confirmed**, and appears only when its supporting event has been confirmed. Its projected midpoint is separately marked as unconfirmed. A notice composer uses that same supported scenario to produce a draft for an operator and an advisory for the customer; it cannot invent a date when evidence is absent. Freshness and provenance let users inspect why a recommendation exists. An overdue or stale status never becomes a fabricated location.

## Technical approach and stack

Vite builds a small Vue 3 application directly, using the same Vite toolchain as Vitest. Vue Router selects account-specific operations and customer views; a static host must fall back to `index.html` for direct links. A shared Pinia store holds shipment events and the scenario clock. It hydrates validated JSON from versioned `localStorage` and saves mutations; invalid or blocked storage falls back to fixtures or in-memory operation. TypeScript contracts define deliveries, shipments, legs, source events, normalized milestones and alerts. Vitest checks normalization, time boundaries, account/site scoping, severity, search, notice evidence, storage recovery and the delivery lifecycle. Dates are displayed as Spanish day/month/year and UTC timestamps. Styling is responsive and operational: dense lists for repeated triage and a shared route/timeline detail for both roles. The `OperatorEventAdapter` interface, `ShipmentVisibilityService`, `ExceptionPolicy` and `NoticeComposer` separate mapping, projection, decisions and copy. Constructor injection enables replacing adapters without a hierarchy of UI classes.

Vue + Vite keeps the dashboard small while supporting both roles; Vite powers development, production builds and tests. A production application would need an authorized API and durable event history; this frontend-only demo provides neither.

## Production path, assumptions and limits

Real integrations would ingest authenticated operator webhooks, EDI feeds or scheduled polls into a queue and immutable event store, with idempotency keys, timezone-aware timestamps, source validation and per-operator adapters. A canonical read model would resolve conflicting updates with explicit precedence and preserve provenance; unknown or contradictory statuses would enter a human review queue. A server would enforce tenant, account, site and role authorization on **every** query and document retrieval. Refresh would use a subscription or polling fallback and display last-successful-sync time; alert delivery would require deduplication, preference management, audit history and approval for customer communications.

Only after historical arrival and incident data exists should a calibrated ETA model be evaluated against simple rules, by route and operator, with confidence bands and drift monitoring. A language model could help draft understandable notices from strictly supplied facts, with structured output validation and human approval. Neither should assert an unsupported date. The next product increment is an authenticated ingestion-and-exception pilot with one operator and a small set of users, measuring status coverage, false alerts, update latency, triage time and customer contacts avoided.

The demo assumes UTC display in Spanish date format, a fixed starting scenario clock that moves to actual receipt time after local edits, and that a customs hold justifies a fixture-supplied later estimate. Saved browser data is local to one origin and device, with no authorization or synchronization. Search and scenario forecasts are deterministic simulations, not an LLM or trained ETA model. Those are product assumptions to validate with logistics teams, not operational rules proven by this prototype. This repository was produced with AI coding assistance; domain decisions, generated fixtures and edge cases must still be reviewed by people.
